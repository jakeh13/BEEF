Correction · step 1

The script the plan said didn't exist

Step 1 was written as "adapt plot_eme_fields() to 1×2's own body cross-section — no companion script exists for this device yet." Both halves of that are wrong. plot_mmi1x2_eme_fields.py has existed since 2026-08-08, commit 76b7465, twenty-three days before the plan was opened — and it had already been run, with all six field components sitting on disk. The plan also counted two call sites for plot_eme_fields(); there are seven.

But the existing script is pinned to the pure-EME configuration, which is the construction the plan's own preamble disqualifies — the 4×4 campaign measured pure-EME missing port crosstalk by 44–62°. So the work was real; it was just retargeting, not authoring.

Correction · frame convention

Every existing field plot is labelled in meow's frame

plot_eme_fields() passes its component string straight to mw.propagate_modes() with no remap. But stack_meow_mode_fields()'s own docstring records that meow's labels are projections onto meow's local axes, rotated one axis from the device frame: device Ex = meow Ez, device Ey = meow Ex, device Ez = meow Ey.

So the panel titled |Ex| below is really the device's in-plane transverse field, and its x axis is device y. The picture is right; the label is not. Harmless for a qualitative look — a real hazard for step 3, which has to stitch these against FDTD fields that are device-frame.

These two panels are also why the plan's step 1 needed more than a re-run. plot_eme_fields() can excite only one mode at a time, and a single eigenmode in a uniform body is invariant along the propagation axis by construction. The panel is correct and tells you nothing about what the body does. An MMI body's entire job is the beating of several modes — which is what the three-panel figure above had to be built to show.

Finding · step 3

The shipped cascade never computes body fields at all

The plan says the cache "persists arrays, never the meow Mode objects". True, but the real situation is stronger. With calibrate_body_neff=True — the default since 2026-08-17 — EMESolver.solve_section() takes its neff_override fast path, and that path, in its own words, "skips the eigenmode solve and mw.compute_s_matrix() outright rather than run and discarded." The body transfer matrix is assembled analytically as a pure diagonal.

Cuts against the plan

The body's mode fields are not merely uncached — under the shipped configuration they are never computed, exactly like the FDTD side. No amount of cache reading recovers them. A separate solve is mandatory, which is what the script above pays for.

Cuts in the plan's favour

A diagonal body transfer matrix means no mode mixing across the body — each interface mode propagates independently, accumulating only phase. Once the profiles exist, the body region is analytically reconstructible, and step 3's genuine difficulty shrinks to the two FDTD↔EME boundaries and the FDTD interiors. The assert_uniform_cross_section guard makes this structural for this device, not a coincidence.

Method note

A wrong inner product, caught by conservation

The first attempt projected the input onto the body basis using a one-dimensional cut through the core. It returned total captured power 1.5857 — impossible for an orthogonal basis — and put 0.5876 on mode 7, an odd mode that a centred input cannot excite at all.

Both artefacts came from the same mistake: a 1-D slice is not the inner product these modes are orthogonal under. field_overlap_matrix() uses the 2-D transverse pair with dy·dz area weights, and switching to that fixed both numbers at once.

The same projection under both inner products. Power conservation is what exposed the error — the parity zeros alone would not have, since they survive either way.

Step 0

The warm re-run answered the wrong question

Step 0 exists because the 2026-08-09 excite-normalization fix has no code-version component in its cache fingerprint, so a pre-fix entry keeps serving silently. The re-run (job 12627197) finished in 43 seconds — fully cache-warm — and came back bitwise identical to the preserved 2026-08-18 output on both ports at all eleven wavelengths.

Why that proves nothing

A cache-warm run re-serves the very entries whose validity is in doubt. A stale entry is expected to reproduce itself exactly. This is the trap the step exists to avoid, and the warm run walked straight into it.

The cold run is the real test

Job 12627227 forces every section cold by pointing save_dir at a fresh cache through a new MMI1X2_SAVE_DIR override, leaving the shared example_sim_cache untouched — fresh-vs-fresh rather than a destructive clear. The discriminator was fixed before the job landed: grep for solve_section: excite band N normalization mismatch.

The prediction is that it stays quiet. This device's smallest excited-mode gap is Δn_eff = 0.0592, four times the 0.0148 that fired the fallback on the modal multiplexer. But Δn_eff is only a proxy for the real gate — a 10% flux-versus-alpha disagreement — so the margin is a prediction, not the measurement. At the time of writing the job had run 19 minutes against a 1:28 precedent, with no warning so far.
